- Use `gh` CLI for all GitHub interactions — code search, reading file contents from repos (via `gh api repos/.../contents/...`), and PR operations — instead of `web_fetch` or `web_search` for GitHub-hosted content. - Before blindly applying bot-generated PR review comments (from gemini-code-assist, coderabbitai, etc.), critically evaluate each comment for validity — not all automated suggestions are correct or worth applying. Confidence: 0.65
- When CI is stuck on a non-substantive post-run cleanup step but all substantive job steps passed, prefer merging the PR directly rather than continuing to debug/cancel/rerun the CI infrastructure issue. Confidence: 0.65
- When merging PRs, use `gh pr merge --squash` with a conventional-commit-formatted subject line and a detailed body explaining the changes, then clean up both local and remote branches. Confidence: 0.60
- Keep PR descriptions in sync with the actual code on the branch — when code is removed, renamed, or modified after the initial PR description was written, update the description to accurately reflect the current state, removing references to code that no longer exists. Confidence: 0.70
- When processing PR review comments, follow a triage-first workflow: fetch all review threads and issue comments, classify each as MUST_FIX / SHOULD_FIX / OUT_OF_SCOPE (with rationale), then stop and wait for the user's go-ahead before applying fixes. The user explicitly asked for the triage table to be presented before any code changes. This avoids reacting to every automated comment and gives the user veto power on cosmetic suggestions. Confidence: 0.75
- When fixing a PR review comment, post the reply directly on the comment thread (not as a summary comment) and include: (a) the commit SHA that fixes it, (b) what was changed and why, (c) a confirmation that local safeguards still pass. Then resolve the thread via the `resolveReviewThread` GraphQL mutation. Issue comments (top-level) cannot be resolved — a reply is the closure signal. Confidence: 0.80
- After processing all PR review comments, post a final summary comment on the PR with: (a) list of MUST_FIX/SHOULD_FIX items fixed, with commit SHAs, (b) list of REJECTED items with rationale, (c) any drift noted between the PR body and the actual code on the branch. This audit trail is useful for code review and future merging. Confidence: 0.75
- When a PR adds multiple commits to fix review comments, prefer separate focused commits per fix (one commit per MUST_FIX, one per SHOULD_FIX) rather than squashing them all together — this makes the commit history useful for archeology later and lets reviewers verify each fix independently. Combine with `Co-authored-by: CommandCodeBot` trailers. Confidence: 0.75
- Before authoring a commit from staged changes, inspect `git status` and `git diff --staged` so the commit message accurately describes the actual staged content (what was added and why) rather than guessing from memory. Confidence: 0.60
